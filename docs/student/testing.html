The portable tests use small generated arrays, miniature binary volumes, temporary folders and miniature RAW tube surfaces. Larger generated 64³ and 96³ voxel configurations also exercise production ROI, editing and frozen-dataset workflows. These checks need no XCAT download, GPU or existing study outputs.

Three distinct kinds of evidence: CPU contracts protect reproducibility and data handling; TensorFlow smoke tests check that a small model really learns, saves and reloads; held-out scientific experiments measure model performance. Passing one is not evidence for the other two.

1. A separate core development environment

Use Python 3.10–3.12; CI runs Linux on both 3.10 and 3.12. Execute these commands from the repository root. A fresh virtual environment keeps installed model backends from automatically enabling their optional tests.

python3 -m venv .venv-core
source .venv-core/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements/dev.txt
python -m pip check
MPLBACKEND=Agg python -m pytest

On Windows activate with .venv-core\Scripts\activate; in PowerShell set $env:MPLBACKEND = "Agg" before running pytest. These are local commands; automated CI currently verifies Linux. The application itself needs only requirements/core.txt. The development profile adds pytest and nibabel to test NIfTI orientation and native-volume comparisons.

pytest.ini makes source, script and fixture imports explicit. The existing tests are also standard-library unittest tests:

PYTHONPATH=src:scripts:scripts/research:scripts/research/evaluation MPLBACKEND=Agg \
  python -m unittest discover -s tests

Dependency ranges are compatibility bounds, not a locked environment. CI publishes the resolved pip freeze alongside JUnit results. Save a freeze file when reproducing a scientific result. The existing requirements/legacy.txt remains a legacy all-in-one desktop/training profile; it is not the student CPU test environment.

Pytest lists skip reasons at the end of every run. Optional model backends, browser checks and a few historical real-study checks with unavailable registry/lock artifacts can skip in a fresh clone. The generated phantom and CPU contract tests do not require those historical outputs. Do not report skipped checks as executed validation.

The teaching entry scripts remain directly under scripts/; optional research commands are grouped under scripts/research/. Reviewed CoA recipes live in configs/case-studies/coa/, reusable technical notes in docs/reference/, and historical experiment settings, reports and provenance in archive/research/. The layout-migration manifest records old and new paths without rewriting signed historical reports. Existing generated output folders retain their paths.

Use outputs/ for generated reports, cohorts and models and scratch/ for disposable experiments. Both are ignored by Git. The data/ folder retains four small legacy geometry examples; the XCAT-derived ACT samples in data/arm.vti and tests/activity_grid_000_001_005.vti are not an attenuation/label integration pack. The software license does not establish redistribution rights for XCAT assets. Source phantoms and generated datasets stay in separately provisioned storage. Model checkpoint formats and tooling caches are ignored throughout the repository. Atlas CSVs, editable INIs, documentation images and PDFs remain version-controlled. Ignore rules do not remove files that are already tracked: inspect git status and the layout contract before submitting.

3. Lightweight voxel integration tests

Run the additional CPU integration tests from the repository root after installing requirements/dev.txt:

MPLBACKEND=Agg python -m pytest tests/integration

The ordinary python -m pytest command and CI discover these tests automatically. No fixture download or optional model backend is required. tests/voxel_fixture.py generates curved, branched vessels and surrounding tissues in temporary folders; Git tracks the generator and tests, not voxel payloads.

ConfigurationWhat it exercisesUncompressed image/label pair
64³ voxelsA curved main artery with an attached branch, a nearby artery and a vein; two soft-tissue source IDs, lung, bone, skin and unknown tissue provide distinguishable reassignment and resistance cases.2 MiB for float32 attenuation and activity labels.
96³ voxelsThe same physical field of view at finer sampling. Both grids include surrounding context for growth beyond the selection tube; fractional control points and anisotropic spacing check physical coordinates rather than integer-grid assumptions. Both resolutions retain the same anatomy-family identity.6.75 MiB for float32 attenuation and activity labels.

Both configurations preserve source-label identity and generate attenuation using the native XCAT-style ATN convention: linear attenuation in cm⁻¹ multiplied by the original i-pixel width in cm. They are calibrated mathematical fixtures, not real XCAT crops or clinical CTs.

The checks cover control-point views and perpendicular cross-sections; stiffness-limited dilation; erosion, release-label reassignment and explicitly configured safeguards; and the path from a validated recipe through frozen metadata to paired image/mask export. The cohort integration tests also verify registry receipts, unchanged neighboring-vessel ancestry and rejection of modified frozen inputs or paired payloads. These are pipeline integration checks, not evidence of model accuracy or clinical realism.

Adding a real crop later: use only assets with confirmed redistribution permission. Save spacing, original full-volume shape, crop origin and affine, tissue/source-label dictionary, reference masks and enough surrounding tissue for the maximum edit distance. Keep the original native-ATN calibration. The generated fixture's reversible crop metadata checks coordinate bookkeeping; it does not establish registration between real RAW surfaces and voxel images. Do not invent a cropped .par file or assume a RAW surface is registered merely because labels match.

Five optional historical-study checks remain separate: they replay saved study records and validate source-file availability and checkpoint/provenance hashes. A crop cannot replace their original receipts. Whole-body source data and full-cohort evaluation remain externally provisioned.

4. Real TensorFlow CPU smoke tests

The core job deliberately has no TensorFlow or PyTorch. Backend-specific tests report skips when those dependencies are absent. A separate CI job installs TensorFlow 2.17.1 and Keras 3.10.0, requires a real CPU runtime, and runs the complete suite with TensorFlow enabled. The focused command below is useful while developing training code.

python3 -m venv .venv-tf
source .venv-tf/bin/activate
python -m pip install -r requirements/dev.txt -r requirements/tensorflow.txt
CUDA_VISIBLE_DEVICES=-1 FAKECT_TEST_TENSORFLOW=1 MPLBACKEND=Agg \
  TF_NUM_INTRAOP_THREADS=1 TF_NUM_INTEROP_THREADS=1 OMP_NUM_THREADS=1 \
  python -m pytest tests/test_tensorflow_steps.py tests/test_segmentation.py \
    tests/test_fixed_refit_smoke.py tests/test_context_learning.py \
    tests/test_multiscale_network.py

The fixed-refit test deletes held-out test payloads before a real fit: any accidental access fails. It then reloads the saved model and checks finite predictions on a differently sized slice. TensorFlow step tests check that changing tensor values does not create new graph traces, invalid input does not update model weights, and real gradients remain finite.

Most existing TensorFlow tests enable themselves when TensorFlow is installed; the context-learning smoke tests additionally require FAKECT_TEST_TENSORFLOW=1. Run FAKECT_TEST_TENSORFLOW=1 CUDA_VISIBLE_DEVICES=-1 python -m pytest to repeat full CI discovery. PyTorch tests still skip when their separate environment is absent. A skipped test is not a passed training experiment.

Wahab GPU use remains a separate, environment-specific integration check. Keep the cluster's supplied CUDA/container stack and validate that environment; do not replace it merely to run CPU tests. Refer to TensorFlow installation guidance and the 2.17 release notes for platform support.

5. Test the ROI report in a real offline browser

The optional browser job uses Playwright and Chromium to exercise the actual HTML controls. It is separate from the core environment. Browser tests require FAKECT_TEST_BROWSER=1 and report skips without that explicit opt-in.

python -m pip install -r requirements/browser.txt
python -m playwright install chromium
FAKECT_TEST_BROWSER=1 MPLBACKEND=Agg python -m pytest tests/browser

The CI browser environment installs Chromium system libraries as well. The browser must be able to open the report with local assets and no external network. Treat navigation, four-panel synchronization, visible coordinates and radius information as interface contracts; numerical tests independently check physical resampling.

6. Optional pretrained segmentation and real XCAT checks

PyTorch, TotalSegmentator and pretrained weights are optional research integrations, isolated in requirements/pretrained.txt. They are not required for the teaching demo or the default CI. When using that environment, run test_pretrained_learning.py to exercise retained output heads, grouped loss, checkpoint strictness and tiled inference. Those tests construct miniature local networks; they do not fetch a vendor checkpoint. Production pretrained inference still requires separately provisioned weights.

Real XCAT runs require authorized source .bin, .raw and parameter metadata with the correct dimensions, physical resolution and anatomical dictionary. The repository's MIT software license does not itself grant redistribution rights to those source assets or pretrained weights. Keep them and generated studies outside tracked source files. The generated teaching phantom is a mathematical test fixture, not a clinical CT or a licensed XCAT example.

Once an instructor has provisioned a real case, repeat ROI review, parameter preflight, freezing and paired export as described in the student walkthrough. Record source hashes, atlas version, saved INI and software revision. Treat clinical performance validation as separate work.

7. Before submitting a student change

  1. Create a feature branch and write a failing test for the changed scientific or data-handling contract. Prefer an analytic shape or tiny volume with a clear expected result.
  2. Run the relevant tests, then the full core suite. For training changes, also run the TensorFlow or pretrained backend tests in their own environment.
  3. For ROI/report changes, open the generated report, inspect the i,j,k and perpendicular views at the first, interior and last control points, and verify radius/coordinate text. Numerical and HTML checks do not replace a visual review.
  4. Check git status: source, INI examples and tests belong in Git; generated volumes, checkpoints and experiment folders do not.
  5. Describe what changed, the contract it protects, exact test results including skips, and any real-case review performed. CI evidence is downloadable from the workflow's artifacts.
