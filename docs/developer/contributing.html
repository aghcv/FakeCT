FakeCT separates source-volume access, physical geometry, morphology, immutable dataset preparation and model experiments. Extend one boundary at a time, document the data contract and verify the expected behavior with a small reproducible example.

1. Choose the implementation boundary

LocationResponsibility
scripts/Argument parsing and workflow dispatch. Keep entry points thin; reusable algorithms belong in src/.
scripts/dev/, configs/development/Import-free developer checks, API generation and the maintained documentation scope.
src/Source adapters, geometry, serial editing, report generation, paired datasets, registries and optional learning backends.
configs/templates/, configs/examples/Reusable configuration contracts and small examples. Preserve explicit units and review flags.
tests/Regression and integration contracts. Prefer generated fixtures to downloaded anatomy or recorded output snapshots.
docs/developer/, docs/reference/Workflow instructions, API contracts and algorithm details. Keep documentation readable offline.
scripts/research/, archive/research/Advanced adapters, case-study utilities and historical evidence. A historical input or result does not establish a portable default.

Use existing configuration objects and stage boundaries rather than introducing a second parser or coupled training-and-generation command. The separate prepare_cohort.py and model_experiment.py interfaces are the default extension points.

2. Make function contracts visible

Start every maintained function with a docstring that states its purpose, inputs and outputs. Use NumPy-style Parameters and Returns sections; add Raises for relevant failure conditions and Notes for units, array order, mutation, filesystem effects or implementation limits. Document public classes and their responsibilities. Private helpers still need a clear purpose and contract.

State exact array shapes, dtypes, coordinate order and units when they affect correctness. Describe optional values and defaults. A function returning None should say what it writes or mutates. Avoid comments that merely restate the next line; explain assumptions, algorithmic choices and invariants.

# Docstring template for a numerical helper; not an additional FakeCT API.
def mask_volume_mm3(mask, spacing_ijk_mm):
    """Measure physical foreground volume from a binary native-grid mask.

    Parameters
    ----------
    mask : numpy.ndarray, shape (k, j, i), dtype bool
        Foreground membership on the native voxel grid.
    spacing_ijk_mm : tuple of three float
        Positive voxel widths in i, j, k order, measured in millimetres.

    Returns
    -------
    float
        Foreground volume in cubic millimetres.

    Raises
    ------
    ValueError
        If geometry is nonfinite or any voxel width is not positive.

    Notes
    -----
    The mask is read only. This helper performs no file or model access.
    """

Use descriptive names and type annotations for new public interfaces. Keep explicit _ijk, _kji, _mm and _mm3 suffixes when an order or unit could otherwise be ambiguous. Prefer named result fields over unexplained positional tuples. Preserve existing API signatures unless the corresponding callers, configuration schema and compatibility policy are updated together.

The API reference is generated from source syntax without importing modules or activating optional backends. Regenerate it after changing signatures or docstrings:

python scripts/dev/build_api_docs.py

Brief headers for tests

Place three comment lines above each test's decorators and definition. State the purpose, the actual fixture inputs, and the expected output or invariant checked by assertions. Inputs can be generated arrays, an INI, mocked dependencies or malformed values. Outputs can be a mask, a file, an exception or preservation of source data; most test functions themselves return no value.

# Purpose: Verify dilation preserves neighboring vessels and protected labels.
# Inputs: Generated CT-like crop, target selector and stiffness-controlled edit recipe.
# Outputs: Growth retains donor lineage; neighboring arteries, bone and skin stay unchanged.

Keep these headers brief and specific to the test. Retain details in the fixture setup and assertions; avoid descriptions such as “tests the function” or “passes successfully.” Use the same format for integration, optional backend and browser tests.

3. Preserve numerical and label semantics

ContractRequired behavior
Index and array orderINI centers and geometry vectors use i,j,k; volume arrays use k,j,i. Convert deliberately, including crop origins and anisotropic spacing.
Physical unitsDistances and tube radii use millimetres; native attenuation images use cm⁻¹. HU conversion belongs in a separately calibrated adapter. A voxel count is not a resolution-independent severity metric.
Label identityKeep original signed source IDs, coarse tissue categories and binary target masks distinct. Never recover an anatomical ID by rounding blended activity values or taking its absolute value.
Source ownershipSource volumes and frozen arrays are read only. Edits operate on explicit copies and preserve ancestry, consistent labels/attenuation and unchanged exterior voxels.
ROI behaviorThe selector identifies original target ancestry; permitted growth can leave that selector. Crop context, edit distance, reassignment search and safeguards remain explicit.
VisualizationDisplay interpolation and downsampling do not change native selection or edits. Coordinate text and perpendicular control-point views must describe the same physical point.

4. Validate boundaries and explain failures

Reject unknown fields, duplicate sections, invalid shapes, nonfinite values, inconsistent point/radius lists and insufficient physical context at the appropriate boundary. Errors should identify the relevant field, invariant and corrective action. Use the existing module's exception types; do not convert a validation failure into a default value, empty mask or apparently successful report.

Catch errors at the command boundary only when producing a clear CLI diagnostic. Avoid broad exception handlers that hide programming errors. Optional backends must remain lazy: geometry, editing and dataset preparation should not require a TensorFlow/PyTorch import or downloaded model. Keep metadata-only validation separate from voxel reads, output writes and model execution.

5. Preserve reproducible releases

Document all file writes and overwrite behavior. Fresh output revisions are required for changed sources, ROI geometry, tissue policy or parameter sweeps. Freeze records bind exact input bytes, dependency hashes and reviewed native preflight. Do not alter a signed receipt, historical source snapshot, published array or checksum to make a revised run appear unchanged.

When implementation changes affect pinned dependency hashes, generate and review a new release. Previously published pairs remain immutable and can be reused by a separately pinned model experiment. Preserve the complete registry tree and explicit source-family grouping. Siblings, revisions and slices from one source family must remain together across training, validation and test assignments.

Use deterministic seeds for generated fixtures and sample selection. Record the software revision, resolved dependency versions and preprocessing configuration for reproducible scientific runs. Generated arrays, caches, checkpoints and scratch work belong under ignored artifact folders, with separate backups.

6. Run development checks

python -m pip install -r requirements/dev.txt
python scripts/dev/check_quality.py
python -m pytest tests/integration
MPLBACKEND=Agg python -m pytest

The static quality check validates source syntax, documented functions in the maintained workflow modules and generic repository language without importing runtime modules. The explicit scope is configs/development/api.json; historical and experimental modules have a separate documentation scope. It complements the regression suite; it does not establish numerical correctness, model accuracy or clinical validity. The testing guide describes backend-specific TensorFlow, pretrained and browser checks, including the meaning of skipped tests.

  1. Add a test for the changed scientific or data-handling contract, using an analytic shape or generated volume with a clear expected result.
  2. Run the smallest relevant tests during implementation and the complete core suite before review. Run the affected optional backend when model code changes.
  3. For reports, inspect the actual offline page as well as numerical resampling tests. Check endpoint and interior control points, native coordinates and physical radii.
  4. Regenerate API documentation, verify relative links and review git diff and git status for accidental data, checkpoint or historical-evidence changes.
  5. Describe the resulting behavior, input/output contract, exact checks and optional skips in the change description. Keep algorithmic changes separate from unrelated formatting.
